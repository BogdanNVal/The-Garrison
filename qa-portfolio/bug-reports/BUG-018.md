# BUG-018 — State-changing actions have no CSRF protection; logout is GET

| | |
|--|--|
| Severity | Medium |
| Priority | Medium |
| Status | Open |
| Build | Current main |
| Area | Security |

## Summary

Forms for add / update / delete / reservation / login do not include CSRF tokens. `logout.php` destroys the session and clears remember-me via a **GET** request, so a simple `<img src="…/logout.php">` on another site can log the user out while they browse.

Admin mutating POSTs are forgeable in the classic “logged-in victim visits evil page” scenario.

## Steps

1. Log in as customer or admin.
2. In another context, trigger GET `/logout.php` (or craft a cross-site POST to `delete.php?id=…` while admin is logged in).
3. Confirm session is gone / action would execute without a CSRF token check.

## Expected

Logout via POST + token (or at least same-site protections); mutating admin/customer POSTs require a CSRF token tied to the session.

## Actual

GET logout succeeds (`302` to login, remember cookie cleared). Delete/add forms have no CSRF field.
